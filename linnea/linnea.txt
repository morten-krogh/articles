Linnea - An HTTP server written in x86_64 assembly with no code dependencies

# Introduction

In the summer of 2026 AI coding agents had gotten so good that 
I became interested in the question of whether they could write code
directly in native code. Could they even do it without using dependencies. 
My first test case was SHA3 hash functions
as described in a previous article. That worked out very well, and I got more ambitious.
I have alsways been interested in high performance web servers and HTTP proxies so that use case

# Linnea

During August of 2026, I wrote, in collaboration with Claude and Codex, a web server called Linnea.
It is open source and available at https://github.com/morten-krogh/linnea
Linnea is a HTTP/1.1, HTTP/2 and HTTP/3 web server and reverse proxy, written in x86-64 assembly running on Linux.
It is comparable to Nginx, Apache, Caddy, etc. It does not have all the features of those esrablished servers, 
but Linnea is actually more advanced and modern in many ways and could always be extended if needed.

A from-scratch HTTP/1.1, HTTP/2 and HTTP/3 web server and reverse proxy, written in x86-64 assembly — with its own TLS 1.3 and no dependencies at all.
Linnea speaks HTTP over TLS to real browsers — Chrome, Firefox and Safari, including HTTP/3 over QUIC — serves static files, and reverse-proxies to backend services. It is built from nothing but nasm and ld: no libc, no OpenSSL, no runtime, no third-party code. The TLS 1.3 stack and every cryptographic primitive under it (X25519, P-256, AES-GCM, SHA-2) are part of the source tree.





# Language and dependencies

Linnea is written in x86_64 assembly which is the assembled into a statically linked ELF binary. 
Linnea's only runtime requirements are the operating system and the processor:
Linux 5.19 or newer, on an x86-64 CPU.
The ELF binary depends only on the stable Linux syscall ABI. There is nothing to install alongside it and nothing to keep in version lockstep.
Linnea is run by starting the executable with a configuration file. 
There is no C runtime. The binary has its own _start; there is no dynamic linker and no libc usage.


uses raw system calls instead of going through library calls. 

No libraries — not even for io_uring, cryptography, or networking. io_uring is driven by hand through the raw syscall interface with no liburing; the TLS 1.3 stack and every primitive under it (X25519, P-256, AES-GCM, SHA-2) are in the source tree; the HTTP, QUIC and socket handling are all direct syscalls.



The entire HTTP stack, QUIC stack, and TLS stack is part of the source tree. The event 
loop and socket operations are handled through the io uring which is the most modern and high performance Linux API for networking. 
Linnea does not use libiouring. It uses the raw system calls of the io uring. For HTTP/2 Linnea offloads partof of TLS to 
the kernel.
 






# How I built it

I wrote Linnea directly on a cloud Linux server 
Local development on my laptop was not used at all.
Codex and Claude ran on the server and write code and did audits. I planned, guided and tested the Linnea server. I did not  
manually read all the code. I did not even have an IDE on the server, just vim. I occasionally looked at code but mostly discussed 
higher level principles with the agents. The agents reviewed each others work and there were multiple audits of the whole code base.
The coding experience was obviously totally different from my previous style of local development with an IDE.
Since the agents ran on a cloud server, there was no downtime just because my laptop was closed.
I used shh, mosh, and tmux to run and communicate with the agents.
During testting Linnea served test pages at a public domain that could inspect in a laptop based browser which also tested 
the actual TLS connections and certificates on the internet.

# What the experiment shows

Linnea can be seen as an alternative to established web servers like Nginx, Apache and Caddy.
It would take extreme amounts of marketing and work to get into that space and that is not my goal of Linnea.
The goal of Linnea is rather to show that it is possible to write the whole traditional stack for a server 
application from scratch in assembly or machine code without dependencies. 
Anyone who is interested can of course use Linnea and contribute to it.
I will write more about my view of the future of software and cybersecurity in later articles. The point of this article was just to 
describe sone high level aspects of the Linnea server.
