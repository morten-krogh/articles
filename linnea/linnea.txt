Linnea — An HTTP server written in x86-64 assembly with no third-party code dependencies

# Introduction

In the summer of 2026, my experience with AI coding agents made me wonder whether they could write
substantial programs directly in assembly, without third-party code dependencies. My first test case was SHA-3 hash functions,
as described in [a previous article](https://mortenkrogh.substack.com/p/an-assembly-implementation-of-sha).
That worked out very well, and I got more ambitious.

I have always been interested in high performance web servers and HTTP proxies, so a web server was a natural next project.
Could the agents help me build the whole application stack, including the HTTP protocols and TLS, from scratch?

# Linnea

In August 2026, I wrote a web server called Linnea in collaboration with Claude and Codex.
It is open source and available on [GitHub](https://github.com/morten-krogh/linnea).
Linnea serves the same general role as web servers such as Nginx, Apache, Caddy and H2O.
It does not aim to provide the full range of features offered by those established servers.

Linnea supports HTTP/1.1, HTTP/2 and HTTP/3 over QUIC, with its own TLS 1.3 implementation.
It serves static files and acts as a reverse proxy to backend services, including support for WebSocket connections.
I use Linnea personally and have tested it
with Chrome, Firefox and Safari. It has not been tested under sustained traffic or by anyone other than me.

# Language and dependencies

Linnea is written in x86-64 assembly and built with NASM and ld into a statically linked ELF binary.
Linnea runs as a standalone executable with a configuration file.

Linnea's only runtime requirements are the operating system and the processor: Linux 5.19 or newer, on an x86-64 CPU.
The binary uses the Linux syscall ABI directly. There is no C runtime, no dynamic linker and no libc usage.
There are no third-party libraries to install alongside it or keep in version lockstep, not even for cryptography or networking.

The complete implementations of HTTP, QUIC and TLS 1.3 are part of the source tree, along with the cryptographic primitives
they use, including X25519, P-256, AES-GCM and SHA-2. The event loop and socket operations use io_uring,
Linux's asynchronous I/O interface. Linnea uses this interface directly, through shared queues and raw system calls,
without liburing. For HTTP/2, Linnea offloads part of the TLS record processing to the kernel while handling
the TLS handshake itself.

# How I built it

Codex and Claude wrote the code and reviewed each other's work. I made most of the architectural decisions,
including the use of io_uring, which HTTP protocols and TLS version to support, and the inclusion of WebSocket proxying.
I also decided what should be configurable and what should be hardcoded. I guided the implementation and tested the server.
I occasionally looked at code, but I did not manually read all of it. Most of my interaction with the agents was about
architecture and behavior. The agents also performed several reviews of the whole codebase.

All development took place on a cloud Linux server, where both agents ran. I used SSH, mosh and tmux to run and
communicate with them, and Vim when I wanted to look at code. There was no local development on my laptop,
and the agents could continue working when it was closed.

During testing, Linnea served pages under a public domain name, which I accessed from browsers on my laptop.
This also tested TLS connections and certificates over the internet.

# What the experiment shows

With my architectural guidance and testing, the agents helped me build a working web server and reverse proxy
in assembly, including its own HTTP, QUIC and TLS implementations, without third-party code dependencies.
Anyone who is interested can use Linnea and contribute to it.

The experiment suggests that assembly is a promising language for future projects developed with AI agents.
The agents seem capable of handling substantial implementation work in assembly, with a human making architectural decisions,
guiding development and testing the result. This makes me interested in exploring how far this approach can go.
