# Programming Languages for an AI World

## The case for custom software and native code

Most programming languages were designed for human programmers. They help us express ideas, manage complexity,
avoid mistakes and work together. Many of our tools serve the same purposes. It is likely that the rise of AI
will have serious ramifications for such programming languages and tools.

As a thought experiment, imagine the infinitely good programmer. This programmer would write the correct program 
directly for the machine and be done. Such a programmer would not need external libraries and dependencies. Such a
programmer would not need a compiler to translate between a source and a target language.
Real agents are far from that ideal. But I still find the thought experiment informative in terms of guiding the
future of programming.

My prediction is that increasingly capable agents will write directly in the platform's executable
language. This is particularly the case for heavily used server applications.
We usually call the C, C++ or Rust program the source and the compiled executable the binary. That distinction reflects
how humans prefer to work. It becomes less useful if an agent can understand and modify the executable directly.

The meaning of native code depends on the chosen execution environment.
For an x86-64 Linux server, native code means x86-64 machine instructions using the relevant Linux interfaces and
calling conventions. For a WebAssembly environment, it means WebAssembly. For a JavaScript engine, it means
JavaScript. The platform determines what is native. There is a slight distinction between assembly code and 
executable code. However, that distinction is hardly important here and for all practical purposes assembly code is native.
The translation from assembly to machine code is deterministic and fast.

I also envision that applications will become more and more customized and
specialized.  Specialization offers the advantage that An application can omit
features it does not need and avoid vulnerabilities specific to libraries it
does not use. For example, there is no reason to use a general purpose proxy
server in front of an application. The proxy server is usually optimized for a
host of use cases that are irrelevant for the application under consideration.

I also believe that applications will be written using close to zero external
libraries and dependencies.  Dependencies used to save programmers enormous
amounts of work. However, they also introduce code, interfaces, updates and
maintenance decisions controlled elsewhere. If agents make implementation and
maintenance much cheaper, the balance has flipped towards no dependencies.

Portability is often offered as a reason to use a higher-level language. For a custom server, however, the
platform is usually known in advance, e.g.e x86-64/Linux or ARM/Linux. Choosing a higher level language 
just to be portable will be unncecessary. If another platform becomes necessary later, 
agents can just rewrite the program in the other language. It is basically a new application with a similar API.

Optimizations are much easier to reason about if the native code is monitored and updated based on execution feedback. 
Transkation or compilation from Another language just makes it harder to reason about. An agent can profile 
a running program, identify an expensive
path and modify its instructions directly. 
For a program that runs continuously on a server, the benefits of optimizing and 
customizing the machine code are obvious. The program runs faster, uses less memory.

Event loops are ubiquitous in server applications. Mostly cross platform libraries such as libev, libevent, libuv, or asio 
are used, or the higher level language comes with its own asynchronous stack. The whole langauge might be more or less 
ergonomic for async programming. In native code with a direct lineage to Linux, or other operating systems, the program could
instead hook into the native APIs such as epoll or io_uring and build state machines around those system calls. Conceptually, the code
becomes simpler to reason about, even though it will be hard for a human to read it, or course.

Security is also easier to deal with in a simpler tool chain. Using no external
librearies will minmize the attack surface. The security of the application can
be made very high by not using any external dependencies, having AI agents
review and monitor the application continuously, and keeping the code secret.
An attacker on the internet will have very little to work with. The information
kwown to the attacker is just the API and the protocols. For example, a
vulnerability in the TLS protocol itself would hurt these applications, but 
a vulnerability in a popular crypto library would not. Existing code can still be reused, but more 
as a guide for custom implementations rather than direct imports.

Besides the programming phase itself, I imagine agents will be involved throughout the life of the application.
The agents will monitor behavior, read logs, trace the executable, investigate
unexpected events, profile expensive paths, test changes and do general maintainance.
